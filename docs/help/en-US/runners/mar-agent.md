# Configure and Use MAR Agent

MAR Agent is built into Node and does not require an external Agent CLI. Every user can add and manage personal models under **Admin → MAR Agent Models**; authorized administrators manage and grant organization models. Users who satisfy both model access and the bound credential scope can select **MAR Agent** for a new session.

## Configure models

**Use resource URLs** requires both the global setting and the model option: the global setting defaults on and each model defaults off. Changes apply to the next execution. This currently applies to images. When enabled, images use fixed signed URLs valid for 24 hours without renewal and are not subject to image-watermark GC. Otherwise, recent attachments and tool images stay visible across requests in a bounded inline window. Inline images and text share GC checkpoints. Historical encoded image payload above 7 MiB triggers oldest-first reclamation down to at most 5 MiB, protecting the latest two successful model rollouts. Text GC can also reclaim mature images above 5 MiB. A request can contain at most 12 MiB of encoded image payload; meeting this limit can override historical-image protection but never discards fresh images. Eviction does not delete attachment or image files. Image attachments remain files with usable paths; the model can reopen an image by attachment path or a `resourceId` owned by the current session. Release notices retain the corresponding resource ID. The tool always reports image dimensions and returns at most 3 MiB per image. Larger images can be explicitly resized with `resize` or inspected locally with `region`; transformation source files can be up to 20 MiB. The image budget excludes text and tool definitions, so it is not a limit on the whole request body. Both modes share independent resource storage, and disabling URLs does not disable vision. Older image-history formats are no longer restored as visual input; their text and attachment files remain. The Node must advertise resource-input support.

Each model is an independent connection. The form offers **Codex**, **ChatGPT plan authorization**, **X subscription OAuth (experimental)**, **OpenAI Responses**, and **Anthropic Messages** as connection types. For Codex, select an existing Codex credential. Enter or edit the model ID directly: there is no catalog picker, and the ID need not appear in the credential's live model catalog. Changing credentials preserves the entered model ID; the display name remains editable. The live catalog is loaded only when you explicitly choose **Load model catalog** for bulk import. Codex uses its fixed service endpoint. OpenAI Responses and Anthropic Messages use an explicit Base URL and inline API key. A new model starts with `256000` context tokens and `32000` maximum output tokens; switching connection types preserves compatible fields, including the model ID, token limits, capabilities, reasoning efforts, and model purposes. Switching between OpenAI Responses and Anthropic Messages keeps the inline API key and custom Base URL; only default addresses change with the protocol. A temporary switch to OAuth and back also preserves the entered key and custom address. OAuth uses fixed endpoints, and an incompatible OAuth type requires selecting another credential. Editing retains saved values; existing keys are not returned to the browser, and leaving the key blank keeps the saved key. Catalog imports preserve limits explicitly supplied upstream. A missing context limit is prefilled with `256000` and can be edited before import; a missing maximum output limit defaults to `32000` (reduced to stay strictly below smaller context windows). Image input, session title generation, Code Mode, Hosted Web Search, Responses continuation, selectable reasoning efforts, and the default reasoning effort are maintained on the model form; transport selection is available for every Responses connection type. When a regular Workspace session or hosted conversation needs a generated title, MAR Agent uses the first enabled available model with **Session title generation** selected, following model order; if none is selected, it falls back to the conversation's current model. The default reasoning effort is always required. Even when no reasoning choices are exposed to users, MAR Agent uses that default internally. For Grok models without configured reasoning choices, unsupported reasoning parameters are omitted on the wire.

Select **Duplicate** in a manageable model’s actions to open a prefilled creation form with a copy suffix in its default name. You can change configuration, credentials, and ownership before selecting **Save**; cancelling creates nothing. Unless replaced, the inline key or compatible OAuth reference is reused securely by the Server without returning secrets to the browser. The new model has an independent configuration ID and is appended to the list; access grants and test results are not copied. Duplication requires management permission on the source, and the new ownership and credential scope are checked again when saving.

Responses models, including inline API keys, can select WebSocket, HTTP/2, or HTTP/1.1 (X subscription supports WebSocket and HTTP/1.1). A failed selected transport does not silently switch protocols. HTTP and WebSocket both allow server-side continuation; switching transport preserves the checkbox. Only HTTP requests with continuation enabled send `store:true`. HTTP with continuation disabled and all WebSocket requests send `store:false`; there is no separate storage setting. With HTTP continuation enabled, the initial request and full-history replays after an invalid reference also ask the upstream to retain responses; consult its retention policy. Enable continuation only when the upstream supports it. A missing or expired response reference triggers one full-history replay within the request attempt budget, provided no semantic output has been committed; authentication, rate limits and unrelated errors are not treated as expired references. Adapter restarts and changed core prompts also replay full history. HTTP continuation requires a Node advertising the corresponding capability. Anthropic Messages prompt caching is managed automatically without this setting.

New model creation and OAuth catalog import both offer **Personal / Organization** ownership to enterprise administrators. Ownership is independent of credential scope: choosing an enterprise credential does not automatically share the model. Create an organization-owned model and then use its authorization action to share it with users, organizations, or the enterprise. Personal models have no authorization action. Editing an existing model shows its ownership without changing it; recreate or import it with organization ownership when sharing is needed. The model list shows the complete manageable set without pagination. Editing, testing, refreshing, and deleting reload the complete current result.

Before the first semantic model output, MAR Agent performs bounded retries for eligible transient connection or service-overload failures. If one model request exhausts its retry budget, the conversation error shows the total attempts and retries while preserving the final cause. A tool follow-up round, recovery request, or later user-initiated run starts again at attempt 1.

MAR Agent does not impose a cumulative token budget or model-round limit on a run, or force finalization based on cumulative usage. Long tasks can continue after Context GC or Compact; context-window checks, cancellation and model-request timeouts still apply. Provider plan, account and request limits are unaffected.

The information icon at the lower-right of a Workspace session shows the latest available Latency and average output TPS. Latency updates after the first valid semantic model response. Average output TPS updates only after the request ends, the provider reports authoritative output tokens, and the summed observed generation duration is at least one second. Shorter windows do not publish a new TPS value; Latency and token usage still update, and the previous valid TPS remains within the same Run. TPS uses client-observed generation intervals, excluding client-tool execution and explicit Hosted Tool execution pauses. Output tokens may include reasoning and tool calls, and network or upstream buffering may affect the observed duration, so TPS is not pure server-side inference speed.

Every user can use the **My model order** tab to arrange their authorized models in the model picker. This does not affect other users, the administrator-defined default order, session title generation, or template candidates. Newly available models that the user has not arranged remain after the saved personal order in the administrator-defined default order. System administrators manage that global default in the **Models** tab, which lists a model’s name, connection type, model ID, availability, access, and test status. The list omits credentials and Responses transport; Codex transport remains available in the model editor. Removing a model does not require disabling it first and is not blocked because the model is currently in use. A model request that has already started may finish naturally, while later attempts to use the removed model fail because it no longer exists. Select **Adjust order**, drag the handle at the start of each row, then select **Save order** to persist the complete order and leave sorting mode. **Cancel** restores the order from before editing.

After saving, select **Test** and choose an online Node whose version, runtime-credential capability, and transport support match the model. The Node performs a real minimal request without creating a Workspace Session or Run. The test dialog stays open after success or failure and shows the result, code, HTTP status, message, Server request ID, and—when the Node provides upstream details—the upstream request ID, content type, `Retry-After`, and response body as selectable plain text. The bounded body may include a truncation notice; HTML is never rendered. Older Nodes may return only the base result fields. Starting another test or changing the model or Node clears the previous result. A failed test still shows the normal error notification, while the diagnostic details remain in the dialog. Lists and test results never reveal API keys or OAuth tokens. Leaving an existing inline key or Codex credential selection blank while editing preserves it. Models remain system-administrator managed, while Codex credentials are managed by the users or administrators allowed by each credential scope.

For Codex (legacy) and ChatGPT models, **Speed** offers **Default / Fast / Ultrafast**. The standard Responses `service_tier` parameter is saved with the model and applies to HTTP and WebSocket requests. Existing Fast settings become Fast; other existing models and new imports start with Default. Availability and usage or charges depend on the upstream model and account; unsupported options are not silently downgraded. Older Nodes can use Fast only if they advertise Fast support; Ultrafast requires an updated Node. The standalone CLI retains `--fast-mode` and `--no-fast-mode` as compatibility options.

## Conversation and auxiliary models

**Conversation model** is checked by default in the model form. Only enabled models with this option checked appear in work-mode and hosted-conversation Composers, Subagent choices, and template main-model choices. Uncheck it to reserve a model for dedicated Compact, session title generation, and prompt prediction. Configure each auxiliary use separately; model and credential permissions still apply. Conversation models can also serve these auxiliary uses. The enabled and session-title switches remain independent.

Existing models retain conversation use, and new or catalog-imported models enable it by default. Changes do not interrupt executions already in progress. Later sends, continuations, or explicit selections using a model that no longer permits conversation use are rejected; select an available conversation model to continue. Conversation history is preserved. If an older Node reports an unsupported capability version, upgrade it before using a catalog containing auxiliary models.

## Prompt Tab model

Under **Admin → MAR Agent Models → Advanced → Prompt Tab**, save the global switch, model, and reasoning effort independently of Compact. The capability defaults to enabled without a preselected model. Users still need model and credential access and can control **Composer Prediction** under **Settings → Appearance** (on by default without a saved preference; an existing Off choice is preserved; Work mode only, saved immediately in the current browser). All four Work-mode Runners are supported. Node uses the MAR Agent SDK's standalone model interface with a result-tool schema to receive prediction data, without creating an Agent session or executing tools. See [Prompt Tab](../workbench/composer.md#prompt-tab) for interaction and data scope.

## Dedicated Compact model

System administrators configure the enable switch, an existing model, and reasoning effort under **Admin → MAR Agent Models → Advanced → Compact**. The setting applies system-wide; it is not on the System Configuration page. Enterprise selection prioritizes root-organization models. It is disabled by default, leaving the current conversation model responsible for compaction. Saved changes apply to subsequent runs, not an active execution.

The Node extension always uses a high-density Textual Continuation IR prompt; there is no per-model option or standalone CLI flag. IR headings and keys use English, while natural-language values may follow the task language. Default compaction and fallback use the Core structured handoff prompt. The dedicated model generates an internal continuation summary without tools or changing the main conversation model. Both Workspace sessions and hosted conversations still require the execution user's model access and credential scope; enabling this setting grants neither. If the estimated input exceeds the dedicated model's window, the first request trims it to 90% of that window, potentially omitting older or lengthy evidence. An unavailable model, remaining context overflow, or failed generation falls back to default compaction with the current model. There is no second capacity-trimming retry of the dedicated model. Cancellation or the total compaction deadline does not trigger fallback. The summary is used for continuation, not displayed as public chat text.

MAR Agent schedules automatic compaction from the latest same-model context-input usage: at 85%, it generates a candidate in the background while the current task and tools continue; at 90%, it waits for that same compaction before the next model request. The conversation timeline updates one item through background generation, waiting, completion, failure, or cancellation. Background compaction does not end the active task or expose its private handoff summary. Messages and tool results produced after the snapshot remain after the compacted prefix. After a successful compaction, if a tail was retained, the Context indicator stays unknown until a foreground model request reports authoritative usage; with no retained tail, the existing `0 / window` reset baseline remains. Background Compact usage still counts toward costs but never replaces foreground context usage, Latency, or average output TPS.

Smart Compaction can request the same background mechanism earlier, at a natural transition into sustained new work. With a valid same-model input watermark of at least 60% and below 90%, the runtime allows the main model to consider whether prior detailed context has low continuation value. It does not trigger for every topic change or one-off question, and it is not a guarantee that all history will fit without loss. Missing or invalidated usage skips this optional opportunity; fixed 85%/90% capacity protection remains independent. There is no extra switch or Enterprise license requirement, and the SDK and CLI use the same mechanism. Existing manual Compact controls and status displays are unchanged.

## ChatGPT plan authorization

The **OAuth credentials** tab lists **Codex (legacy)**, **ChatGPT plan authorization**, and **X subscription** in one table. To add a ChatGPT credential, select **ChatGPT plan authorization** and an online Node on the computer running your browser. The Node must support local sign-in. Open its local sign-in link and complete authorization on OpenAI's page. A remote Node cannot receive this browser's loopback callback; cancel and select the local Node instead.

The local Node is only a temporary sign-in provider. Server stores the credential and owns token refresh. Other authorized remote Nodes can share it without signing in themselves. Personal, organization, and enterprise scopes use the same management and model-use permissions as Codex credentials. Reauthorization also needs a local Node and reuses the issued client ID. Cancellation or failure leaves the existing credential intact.

Models use the fixed public OpenAI Responses endpoint, not the legacy Codex backend. HTTP/1.1, HTTP/2, and WebSocket are supported. HTTP and WebSocket can use `previous_response_id` for incremental user and tool turns; WebSocket additionally requires one healthy connection. Reconnects or adapter rebuilds replay the necessary full history. Image generation with this credential is not supported. An optional SOCKS5 proxy applies to Node sign-in, Server refresh and catalog requests, and inference on execution Nodes.

A successful identity sign-in without plan-use permission is retained as **Unauthorized**. It cannot load models or run inference: sign in again and grant plan usage. This is not token expiry and never switches automatically to API-key billing. Legacy Codex private usage queries are unavailable for the new type. Its account identifier comes from verified identity; provide missing context-window limits when importing models. Tokens are never returned to the management page.

Select **Manage usage** in a ChatGPT credential's **Details** to open [ChatGPT Settings → Usage](https://chatgpt.com/settings/usage) in a new tab, review plan or app limits, and adjust available settings. Make sure ChatGPT is signed in to the account associated with that credential. For `subscription_sharing_usage_limit_exceeded`, the chat error message explains the usage limit and asks you to open `https://chatgpt.com/settings/usage` in plain text, without an additional button or interactive link. Other HTTP 429 errors are not treated as exhausted plan usage.

## X subscription OAuth (experimental)

Under **OAuth credentials**, choose **Add OAuth credential**, select **X subscription OAuth (experimental)**, and enter a name, ownership, and optional SOCKS5 URL. Open the displayed xAI authorization page and enter the device code; no local Node is required. Check the authorization page and selected account before approving. The shared public OAuth client may appear as Grok Build. Inference access depends on upstream account and subscription eligibility; neither a payment amount nor a successful sign-in guarantees model access.

Use `socks5://[username:password@]host:port`, URL-encoding special characters. The same proxy applies to Server device authorization, token exchange, identity, refresh, catalog, usage and revocation requests, and to model requests from the execution Node. Proxy failures never fall back to a direct connection. Both Server and the execution Node must reach the proxy; `127.0.0.1` on a remote Node is not the Server's localhost. The browser authorization page uses the browser's own network, not this proxy. You can edit or clear the proxy later and inspect its full URL in credential details; do not share screenshots containing proxy passwords.

After signing in, load and import the catalog, or create a Grok model, select the credential and enter a model ID. Inference uses `https://cli-chat-proxy.grok.com/v1` with a choice of WebSocket or HTTP/1.1 SSE; new models and catalog imports default to HTTP/1.1 SSE. Responses continuation is off by default, so both transports send full history. You can manually enable `previous_response_id` with either transport. Support depends on the upstream and account; enabling the setting is not a compatibility guarantee. Transport and continuation support on the subscription proxy are not guaranteed. A missing reference falls back once to full history; other failures retain diagnostic details. Speed tiers, HTTP/2 and image generation are unavailable for this connection. Models still use the X subscription OAuth credential, not a developer API key; catalog, identity and usage queries remain on the subscription proxy. Upgrading Server moves subscription models mistakenly configured with the developer API URL back to the subscription proxy while preserving other settings and clearing old model test results. Hosted Web Search can be toggled on the model form; new models and catalog imports enable it by default. Existing models keep their saved value; edit, enable the checkbox and save to turn it on. Re-importing creates independent models rather than modifying existing ones. The execution Node must advertise support for the new Responses parameter capabilities; otherwise upgrade Node.

Choose **Query usage** in credential details to manually load the current used/remaining percentage, weekly/monthly period, reset and query times, and the separate additional USD balance. Missing values display as a dash, not zero or unlimited. MAR does not estimate remaining tokens or display nonexistent token totals. A failed usage query does not imply inference is unavailable. Usage is not polled automatically and is cleared when details close. Upstream accounts may have additional paid balances; MAR does not top up or change billing settings and does not guarantee that subscription calls never incur extra charges.

Server stores and refreshes tokens; the execution Node receives only short-lived access credentials. Sign in again when authorization expires. Deleting an unreferenced credential attempts to revoke its upstream refresh token and reports revocation failure. This integration depends on a changeable subscription proxy protocol and is not recommended for production tasks requiring a stable SLA.

## Configure Codex credentials and the model catalog

Every user can open **Admin → MAR Agent Models** for **My model order** and the Codex credentials they may manage; only system administrators see the **Models** tab used to configure models. A regular member can create only a personal credential. An organization administrator can also select an organization in their managed subtree, and a system administrator can select an organization or the entire enterprise. A personal credential is visible only to its owner, an organization credential is visible only to system administrators and organization administrators whose managed subtree covers it, and an enterprise credential is visible only to system administrators. Select **Add OAuth credential** and choose **Codex (legacy)**, enter a name, scope, and optional SOCKS5 proxy, then start device sign-in. This proxy applies only to Codex OAuth requests, model-catalog requests, and Codex model requests that reference this credential. The system polls automatically at the Server-provided interval, and you can select **Refresh sign-in status** while waiting to query immediately. A credential is stored only after sign-in, token exchange, and account validation all succeed. Cancelled, failed, or expired attempts create no credential.

The credential list and Details show the current access token expiry and the earliest refresh time supplied by ChatGPT. An unknown earliest refresh time appears as a dash; neither timestamp is the refresh token expiry. While refresh authorization remains valid, Server renews near-expiry tokens automatically. Nodes also renew access tokens and runtime tickets during long tasks without waiting for another model call, with bounded retries after temporary failures or unchanged near-expiry tokens. Persistent disconnection or invalid credentials still require recovery or sign-in. Manual refresh can request renewal before that time; the upstream response decides whether renewal succeeds. Automatic renewal still respects the earliest refresh time. Actual renewal immediately updates the list and open Details with the new expiry, earliest refresh and last-refresh time. The action column provides **Details**, **Edit**, **Test**, and **Remove**. **Edit** can change the name, scope, and SOCKS5 proxy. Narrowing a credential scope is rejected while an existing model grant remains outside the proposed scope; narrow those model grants first. Details fetches that credential separately, displays the complete SOCKS5 URL verbatim, and provides refresh, sign-in-again, query-usage, and model-catalog actions. **Query usage** displays lifetime tokens, usage on the previous Los Angeles day, the total for seven consecutive calendar days, the current used percentage and reset time for each quota window, and the query time. The previous day’s date and UTC offset appear in smaller text below its usage value. If no bucket exists for yesterday, that date still appears while usage shows a dash; an older bucket is never substituted. A bucket for the current Los Angeles day remains excluded from the seven-day total. Statistical days roll over in `America/Los_Angeles`: `UTC-07:00` during daylight saving time (15:00 in UTC+8) and `UTC-08:00` during standard time (16:00 in UTC+8). The system does not poll usage automatically, and closing Details discards both the complete proxy string and the usage result. A credential referenced by a model cannot be removed until that reference is changed or removed. The page never displays custom metadata, imported-model counts, access tokens, refresh tokens, ID tokens, the raw upstream usage response, or a FedRAMP flag.

Select **Load model catalog** to read the live Codex catalog visible to that credential. Each row shows the reasoning efforts supported by this system, including `ultra`, the catalog-provided or normalized default effort, and any genuinely unknown upstream efforts. Select the models to import and provide a context window only when the catalog omits it; a missing maximum-output value does not create an input field. The catalog has no availability switch, and imported models are enabled with the catalog default. Configure transport and Responses continuation later in the model view. Every Codex or ChatGPT catalog import creates a new independent model, even for the same credential, upstream model ID, display name, and ownership. Existing models and grants remain unchanged; new models use the import defaults and do not inherit existing settings or grants. If the live catalog changes, the page asks you to review the refreshed catalog before retrying.

## Configure model access

New models are **Restricted** by default. Models that existed before this access feature are migrated as **Public**. The **Access** column shows the current state:

- Granting access to the **Entire enterprise** makes the model public.
- Without an entire-enterprise grant, access can be granted separately to users or organizations and the model remains restricted.
- System administrators can always manage every model regardless of model-grant records, but actual use still requires the user to be inside the bound credential scope.

Select **Grant** on a model row to view, add, or revoke grants. A model's grant range must be fully contained by the bound credential scope; for example, a credential owned by an organization cannot be granted to a user or organization outside that subtree or to the entire enterprise. A regular user's new-session model catalog contains only redacted models that are enabled, granted to that user, and backed by a credential whose scope contains that user. The main Agent and its subagents receive the same authorized model set.

Disabling a model rejects subsequent new sessions, messages, and session commands. Revoking a user's grant, moving the user outside the credential's organization scope, rebinding or unbinding the model credential, or making the credential unavailable also causes every subsequent runtime credential resolution to be rejected. Work already accepted by Node and no longer requiring credential resolution is not forcibly terminated. When an existing MAR Agent conversation is opened and its saved model is no longer in the current catalog, Web automatically saves the first available model and switches the reasoning effort to that model's default. If the catalog is empty, Web does not switch to another Agent. A model can be deleted directly without disabling it or waiting for active tasks. Executions that already obtained the configuration can continue, while later model resolution fails as not found.

## Sessions and permissions

Supporting Nodes (0.10.25 onward) offer **Auto** and **Full access**. New ordinary work sessions default to Auto; existing sessions retain their saved setting. Entering a Goal never upgrades MAR Auto to Full access. The standalone SDK/CLI still defaults to Full access, and hosted conversations keep their existing isolation and permission policy.

Auto uses the current model's judgment: routine engineering and explicitly authorized work continue automatically; material risk or unclear authorization produces ask. Deny is reserved for an effective explicit prohibition, higher-priority/Host prohibition, or known extreme danger whose impact cannot reasonably be bounded. Authorization is reused within the same task, target and impact, across tools, retries, turns and subagents; material expansion or withdrawal requires reassessment.

For Code Mode, the model is guided to declare ask/deny for the whole outer `code_exec` call. A nested deny skips only that tool and returns `error: MAR_AGENT_PERMISSION_DENIED` with a short `message` in the result data. It does not throw a JavaScript exception or end the cell; check the result before dependent steps. The denied tool is still recorded as failed. Other errors keep their existing behavior.

Ask waits online through the Runner approval card, showing the public reason, command/arguments/code, working directory and expiry. Allow executes the captured original call; concurrent requests are decided separately. After 10 minutes without a decision, the request expires without executing and is not treated as a user rejection. Rejection, expiry and model-declared deny fail only that call; the model can continue within remaining authorization or stop naturally, but must not retry or route around a user refusal. Cancelled, decided or expired cards cannot execute. Goals and schedules retain existing Node policies. Standalone SDK/CLI hosts without an online channel stop on ask; later instructions do not replay the old call.

**Auto is neither an operating-system sandbox nor an independent safety reviewer.** Full access omits Auto self-assessment. Both retain Host path/resource validation and use the Node service account's actual permissions. Use a dedicated low-privilege account and appropriate Workspace and host permissions. Older Nodes do not show Auto; upgrade or explicitly select Full access rather than silently downgrading.

Native session records are stored under `~/.mar/agent/sessions/` for the Node service account; Server does not store conversation bodies. MAR Agent supports Plan, Compact, question, Todo, MCP, images, and subagents. Each subagent is an independent persistent child session with its own history and parent relationship, while the default session list shows only user root sessions. Subagents cannot delegate recursively. Continuous tasks use Node's shared Goal workflow and are not reimplemented inside the Agent SDK.

MAR Agent scans standard Skill directories under HOME and the Workspace and initially gives the model only each Skill's name and purpose. When a request clearly matches a Skill, MAR Agent loads that Skill's complete workflow and resource directory; users do not need to name it. For duplicate names, Workspace Skills take precedence over user Skills, followed by SDK built-ins. Project guidance cannot change tool parameters or host permissions.

### Command environment

`exec` enables login initialization by default. Bash reads the first readable file in its native order: `~/.bash_profile`, `~/.bash_login`, then `~/.profile`. It also loads a readable `~/.bashrc` when `BASH_ENV` is unset or empty. PowerShell loads its native startup configuration by default. These files belong to the Node service account, not the browser user. Configuration is read on every command start; hosted conversations read only files visible inside their isolated environment, never the host account's configuration.

To skip login initialization, ask the Agent to use `exec({ command: "…", login: false })`. A login Shell is still noninteractive. If a toolchain PATH appears after a noninteractive `return` in `.bashrc`, put that shared environment configuration in a login profile or before the early return. MAR does not bypass that guard, and an `export` in one command does not update Node or subsequent independent commands.

### Advanced subagent control

By default, model tools can create up to 16 child sessions per parent Execution. Up to 16 child-agent turns run concurrently under the same parent session; additional turns queue and start automatically when a slot becomes available.

Child-agent tools are `agent_start`, `agent_wait`, `agent_message`, and `agent_cancel`. Use the returned `agentId`, which is also the child session ID. `agent_start` returns identity and status after registering the child session and task, without waiting for completion. It does not accept a `background` parameter. The parent can continue independent work and use `agent_wait` when it needs the child result. `agent_message` defaults to `delivery=append`: it starts a turn when idle or adds guidance after the current complete model response or tool batch. Explicit `delivery=replace` immediately requests cancellation, waits for the current turn to close, and starts the new message in the same child session without rolling back completed changes. The returned `messageId`, `turnId`, and `deliveryStatus` distinguish accepted input, input applied to persisted context, and cancellation or failure before application. Applied does not mean the model has completed the requested guidance. Use `agent_wait` for the latest receipt; `waitMs=0` returns status immediately. Use `agent_cancel` to stop without sending another message. Unfinished turns appear as interrupted after a restart and require an explicit message to continue. Start shell processes with `exec`, then use `exec_wait` with `processId` to wait, write stdin or cancel. The old tool names and `taskId` field are not supported.

Unread public child messages and new terminal results are delivered automatically before the parent's next normal model request, including direct children created through the native Extension API. The parent need not repeatedly use message waits to check progress. Delivery does not wake an idle parent or postpone a normal final answer: join results required for delivery before finishing, and use `agent_wait` when genuinely blocked. Automatic delivery and model waits share their observation position, so subsequent waits do not repeat already delivered message bodies or terminal evidence. Child content is context to verify, not new user instructions or authorization.

`sleep({ durationMs })` provides a bounded delay of 1 to 1800000 integer milliseconds (up to 30 minutes). Accepted user input or an unread public subagent message ends the wait early; messages are then automatically injected and marked read through the normal path, without repeated wake-ups. It does not monitor external conditions or wake on process or cell completion; use the corresponding wait for an existing resource. The model always calls `sleep` directly, never inside a Code Mode cell.

`agent_wait` also supports an explicit group of child agents:

```js
agent_wait({
  agentIds: ['a', 'b', 'c'], // Replace with IDs returned by agent_start.
  mode: 'all',
  waitFor: 'completion',
  waitMs: 300000
});
```

`agentIds` must contain 1–8 distinct IDs and cannot be combined with `agentId`. `mode: 'any'` (default) returns when any selected child satisfies the condition; `mode: 'all'` waits for every child. `waitFor: 'completion'` (default) waits for terminal states; `waitFor: 'message'` waits for each target's latest unread public message or terminal state, not ordinary tool activity. Failed, cancelled and interrupted turns are also terminal, not successful. A group shares one timeout and returns `agents` in input order, an overall `waitOutcome`, and `pendingAgentIds` for unmet conditions; a timeout can include partial results. `waitMs=0` returns status snapshots without reading or consuming unread messages. Cancelling a wait does not stop child tasks. Single-agent and untargeted calls remain unchanged.

### Web search and fetch

When Hosted Web Search is enabled, both Auto and Full access use the selected model service's native hosted search without a client permission declaration; self-hosted search is not exposed at the same time. Otherwise MAR Agent uses the SearXNG service bundled with Server Compose. Web Fetch connects directly from the Node, does not read model credentials, and never inherits the SOCKS5 proxy configured on a Codex credential. It can reach any HTTP/HTTPS IP address or domain available from the Node, including intranet resources. It accepts self-signed or otherwise untrusted HTTPS certificates by default; set `MAR_AGENT_WEB_FETCH_ALLOW_UNTRUSTED_TLS=0` in the Node service environment to enforce certificate verification.

Node injects Web tools for the current Execution; they are not built-in Agent SDK network capabilities. `web_fetch` requires either `http` (raw text/HTML without JavaScript) or `browser` (visible text and title rendered by isolated headless Chromium). There is no `auto`, default mode, or automatic fallback; the model can explicitly choose another mode. Each child agent receives the search directory for its selected model rather than inheriting the parent model’s choice. Browser reads do not share user login state or cookies and expose no click, login, arbitrary-script, or download API. Hosted conversations with network policy `NONE` receive neither Web tool; web-enabled hosted reads always verify HTTPS certificates.

Node prepares Chromium during installation/upgrades, never during startup or fetching. If it cannot start, check the service account cache and Linux system libraries. See [Install and Register a Node](../deployment/node-installation.md#web-fetch-browser-preparation).

## Image generation configuration and use

### Configure image models

In the separate **Image generation** tab, every user can add, edit, remove, and enable personal image models. Authorized administrators manage and grant organization image models.

Select **Adjust order**, drag the order handles, then select **Save order** to apply the priority. **Cancel** restores the original order; other configuration changes are disabled while sorting.

Codex uses a credential and model ID. Volcengine Ark uses an API key, model ID, and full image-generation endpoint URL shared by generation and editing. Model IDs and URLs have no defaults and must be entered explicitly. Use HTTPS without embedded credentials, query parameters, or fragments. Existing Ark entries require a URL before they can be used. Ark keys are write-only; leaving the key blank when editing the same entry preserves it.

### Request generation or editing

Each Run selects only the first enabled image model available to the current user. Codex requires an in-scope credential that does not need sign-in again; Ark requires a configured key. Unavailable entries are skipped; text tasks still work when no image model is available. Changes apply to the next Run, and failed requests do not automatically switch providers. Regardless of the text model, including TEXT-only coding models, MAR Agent exposes only the selected provider’s `codex_image_gen` / `codex-imagegen` or `byted_ark_image_gen` / `byted_ark-imagegen` tool and Node-provided Skill. These tools are available to the root Agent, not Subagents. Both support text-to-image and reference-image editing. Ark produces a single 2K PNG and does not support image groups. Request image generation or editing directly; no Skill installation or explicit Skill name is needed. Agent instructions require loading the Skill before performing image work you requested or explicitly authorized, rather than adding unsolicited images. Only the name and purpose are initially included in context; complete guidance is loaded on demand without creating Skill files in HOME or the Workspace. It does not provide an additional Python CLI or API-key fallback.

## Code Mode tool orchestration

The subagent collaboration controls `agent_start`, `agent_wait`, `agent_message`, and `agent_cancel` are always direct-only. Even with Code Mode Only enabled, the model calls them directly, never through `tools.*` inside a cell. Child agents can still use Code Mode according to their selected model configuration.

Code Mode is disabled by default. MAR Agent exposes a restricted JavaScript orchestration cell only when **Code Mode** is enabled for the selected model and the Host supports execution. The main Agent and Subagents use their respective model settings; protocol type does not imply support. A cell can compose permitted tool calls and emit only the results needed, reducing intermediate model round trips. Enabling the switch defaults to **Code Mode Only**: programmatic tools, including single-tool operations, use `code_exec` by default; direct-only tools and tools explicitly exposed in both places keep their direct entry points. Disabling it restores ordinary direct calls. Only controls tool exposure and model guidance, not additional permissions; dispatch still follows caller permissions, discovery state, and Host policy. Configuration changes apply to the next execution, not one already running.

With Code Mode enabled, `apply_patch` and `exec_wait` remain available both directly and programmatically. The model chooses either entry point for `apply_patch`; for a single process wait, prefer direct `exec_wait`, while concurrent waits or composed processing can use `tools.exec_wait`. Do not wait for the same process through both entry points at once. Default exposure for other tools and existing caller permissions remain unchanged.

Each cell uses a fresh QuickJS WASM runtime in a Host-managed worker process. Top-level `await` and `Promise.all` are supported; Node globals, module imports, native file/network APIs, and `console.*` are unavailable. Emit text explicitly with `out.text(value)` and returned tool images with `out.image(value)`. Text output recursively replaces the `dataBase64` string of structured `image/*` objects with a compact placeholder, leaving the original object intact. This does not send pixels; use `out.image` separately. Prefer `result.data` or `result.content` for text; explicitly supplied strings are not parsed or screened for Base64. Files, commands, and network access require explicit `programmatic` permission on `tools.NAME(input)`, retaining each tool's own authorization and safety checks. Results use a shared envelope: raw file text is in `result.data.results[0].text`, not the line-numbered `content` display.

`code_exec`, `code_exec_wait`, `tool_search`, `question`, and direct-only tools cannot run inside a cell. Ordinary external MCP tools have programmatic permission by default and run through Code Mode in Only mode; explicitly direct-only tools remain direct. Discover deferred tools with a direct `tool_search` call. Search results carry names, descriptions, and input definitions without growing the Code Mode description; discovered programmatic tools become callable in a cell from the next model response. Await every tool call. Language isolation does not replace Host file permissions, process controls, or OS sandbox policy, and does not make writable tools read-only. Input and text output are each limited to 1 MiB, with up to 128 tool calls per cell. Synchronous JavaScript execution has a 120-second budget; asynchronous tool waits do not consume it, and cells have no fixed wall-clock deadline. Cancellation, timeout, or output limits may follow completed operations; failure does not roll back changes. Start background processes with `tools.exec({ command, ... })` inside a cell, then use direct `exec_wait` or `tools.exec_wait` inside a cell with the returned `processId`. It defaults to waiting and also supports `action: "write"` and `action: "cancel"`. Both process tools support direct and programmatic calls; Only mode exposes `exec` through Code Mode and keeps both entry points for `exec_wait`. Waits inside a cell still follow individual tool timeouts and Host policy. `exec` no longer accepts the old `action` parameter. The initial wait defaults to 10 seconds, capped at 30 seconds; `exec_wait` defaults to 10 seconds, capped at 300 seconds. Explicit `yieldMs: 0` returns immediately. Cancelling a wait does not terminate the process, and wait windows do not extend the process timeout.

Background cells are Session warm resources. The initial `code_exec` wait defaults to 30 seconds; `code_exec_wait` defaults to 10 seconds. Explicit wait values do not change nested tools' wait windows. `cell.yield_control()` ends only the current wait and flushes available output; JavaScript continues in the background. An optional first line `// @options: {"yieldMs":30000}` sets the initial wait window; the Runtime fixes the output budget. Use direct `code_exec_wait` with the returned `cellId` for incremental output or completion; `action` defaults to `poll`; `action: "cancel"` explicitly stops the cell. Ending or cancelling a model Execution does not stop a registered cell. A later Execution can take it over using retained-resource hints. Session resource cleanup, timeouts, and Host disposal stop cells; JavaScript execution is not restored after a process restart. Terminal results have a bounded cache, with repeat reads marked `cached: true`.

Temporary resource handles have type prefixes: a `cellId` is `c_` followed by 12 lowercase hexadecimal characters, and a `processId` is `p_` followed by 12 lowercase hexadecimal characters. Copy the complete returned ID unchanged; do not shorten or interchange IDs. Use `code_exec_wait` for cells and `exec_wait` for processes. A wrong-type handle returns `MAR_AGENT_RESOURCE_HANDLE_TYPE_MISMATCH` with the appropriate tool hint; it never redirects the operation automatically. A prefix does not prove that a resource is still available or accessible. Existing Session ownership and cleanup rules remain unchanged.

Process waits aggregate stdout/stderr until output closes after termination or the wait window ends. New logs do not end the model's wait early. Web command cards can show bounded live previews without extra model requests or consuming the final tool output. Cancellation and user follow-up messages can still end a wait early while the process keeps running.

The Web conversation displays each `code_exec` call as a command card with its original JavaScript and call output, without expanding nested tools. Live logs from nested processes appear on the outer code card. After a cell returns running, an active wait card in the same execution continues showing its progress; the final tool result replaces that temporary preview. `code_exec_wait` also uses a command card for waiting or cancellation results. A returned command card does not mean a yielded background cell has finished.

## Local SDK and CLI

`@myagentroam/agent` is an embeddable TypeScript SDK and provides the single `maragent` command. The CLI uses MAR's own model catalog under the current user's HOME. It does not read Server model settings and does not automatically discover Claude, Codex, or OpenCode configuration. A model can use a static API key or the `CODEX_AUTH_FILE` credential source. The CLI reads a Codex ChatGPT OAuth file only when the user explicitly supplies `--codex-auth-file PATH` for the current command. The path and tokens are not written to the model catalog, Session, logs, or events, and the CLI never refreshes or rewrites the file. Run `maragent --help` for execution, resume, session, and model commands.
