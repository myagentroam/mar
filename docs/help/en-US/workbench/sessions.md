# Create and Manage Sessions

On Nodes that advertise grouping, **Main Sessions / Child Sessions** separates the session list and defaults to Main Sessions. Sessions with a parent relationship appear under Child Sessions; sessions without one appear under Main Sessions. Search and pagination stay within the selected group. Switching groups does not close the conversation or interrupt work. Each Workspace remembers its group for the current page only; reloading defaults to Main Sessions. A Node without grouping capability retains the mixed list.

Group tabs show only their names and selected state, without running counts or unread badges. Clicking a tab only switches the list; it does not open a session. Individual session rows retain their running and unread indicators. Notifications, recent-session items, and Workspace tabs synchronize Main / Child Sessions when they open a target session.

Click or tap the conversation title to share or rename the session, view its collaboration network, or manage its prompt and scheduled task where supported. Use the session list's More menu to pin, reorder, or delete it. **Copy session ID** is available from the title and list menus; the ID is not shown in the header.

Open the **Collaboration Network** dialog from the icon beside the title, the title menu, or the list menu. Open it from any level in Main or Aside to see that session’s ancestors, siblings, and other connected branches. The session you open the dialog from keeps its blue Current session outline even when you view another collaboration whiteboard. Large networks show a notice if the display limit is reached. Solid arrows point from parent sessions to their children; dashed lines indicate a currently shared collaboration whiteboard. Collaboration whiteboards are not nodes. The graph automatically scales and centers the current session. Use the mouse wheel or zoom buttons to zoom from 10% to 100%, and drag to pan. On a phone, drag with one finger or pinch with two fingers to zoom. The right panel starts with the current session’s collaboration whiteboard. Select a node to see its own board, or select a dashed line to highlight the relationship and see its shared board. Select a node again to return to that session’s own board. Board entries and recent changes are shown directly and cannot be edited. Use a session node’s **More** (···) button or right-click the node to open that session in Main or Aside. Closing the dialog leaves the current session unchanged. Older Nodes without network support continue to open the session tree from the same entry points.

A session can be open in both the main work area and Aside. Opening either side does not close the other, and reopening the same location does not refresh its conversation. Each Workspace keeps independent Main and Aside drafts for message text, skill tags, and references. Switching sessions or starting a new session on one side preserves its input; switching Workspaces restores that Workspace's draft for each side. Even the same session has independent input on both sides, while concurrent duplicate submissions are still prevented. Queued-message edits remain bound to their original session. Closing an Aside session tab stops displaying the conversation there; it does not end the Agent's task, delete the session, or close the main work area.

In work mode, closing a Workspace preserves its drafts in the current browser tab for reopening. Signing out or losing authentication clears that tab’s saved input drafts and queued-message edits so another account cannot restore them. Save important unsent content elsewhere first. This does not delete messages already sent or queued.

Aside keeps at most one session tab per Workspace. Opening another session replaces the previous session tab while preserving Aside's current input and leaving the previous session's task running. Tool tabs such as Files and Terminal are unaffected.

Agent operations and messages from other sessions appear in the [Agent collaboration](conversation.md) group inside the work process. The group does not provide session shortcuts. To view a target session, send a message, or stop its run, open it from the session list or collaboration network. Normal session permissions still apply.

When an Agent sends a message or sets a Goal on an ancestor session that has ended or is stopping, the operation returns `AGENT_ANCESTOR_NOT_ACTIVE` without restarting it. Sending works again once the ancestor is running. Users can still resume sessions manually.

Expand an execution record to inspect the available command or code, output, working directory, exit code, and status. Each call has its own record. **Copy public record** copies that record's available public information, which can be truncated; older Nodes may provide fewer details.

A regular work session must execute in the selected Workspace's valid root or a subdirectory. An independently registered Git worktree uses its own Workspace. Node rejects new execution if the directory disappears, the registered root is replaced, or a link escapes the Workspace; it does not silently switch directories. If queued messages are paused for this reason, restore a valid directory and use **Resume** in the queue. Messages and attachments are retained and can still be removed through the existing queue controls. This check does not make work mode a host filesystem sandbox or change hosted-conversation isolation.

When there is no session to restore, the main work area shows a new session draft, even if the list contains previous sessions. Start typing or select an existing session from the list. A new session is created only when its first message is accepted. On supported Nodes, selecting **New Session** or using its shortcut switches the list to Main Sessions. Manually switching groups afterward does not change the Composer draft.

The session list initially loads up to 30 sessions. Scrolling near the bottom automatically loads up to 30 more; search results continue in the same way. New sessions remain visible in the current list. A small ring marks the pending page. A failure preserves the loaded sessions and pauses automatic loading; select **Failed to load. Retry** at the bottom to continue. Retrying shows only the ring.

An initial or earlier-history load failure does not trigger repeated automatic requests. Select **Failed to load. Retry** in the conversation to read again; loading and retrying show only a ring. The same failure does not also produce a popup. The retry control's supplementary hint retains available error codes, details, and request identifiers. Established realtime subscriptions have bounded recovery, and reconnecting the page rebuilds subscriptions. These read or subscription recoveries never rerun an Agent task.

A conversation turn can contain several collapsible **Work processes**. Public reasoning text, tool calls, and file operations appear in their actual order; Agent replies, approvals, and questions remain outside these groups. The active process opens by default and collapses when finished; your manual expansion or collapse takes precedence. Missing public reasoning does not create an empty card, and reasoning text is not an execution status. File details still open in the existing dialog.

A reasoning preview appears above each process status row and in collapsed reasoning rows. It uses the latest valid public reasoning record within the corresponding scope, whether a summary or visible content, and extracts the first clause of its first non-empty line after removing leading heading or bold formatting. An older summary does not override later reasoning. Long previews use a single-line ellipsis according to the available width. Expand reasoning to read the full original text; a preview does not indicate execution status.

Scroll upward to the top of the conversation to load earlier messages. Earlier content is inserted above the existing messages while preserving your current message and its position in the viewport, without jumping to the start of the new page. Continue scrolling upward to read the earlier messages. If the top history marker remains in the viewport after the initial load, one additional page loads automatically while preserving your reading position; this does not continue through the entire history. No load button appears while idle, and loading or retrying shows only a small ring. After a failure, select **Failed to load. Retry** without clearing the messages already loaded. Once all history is loaded, no loading control or beginning-of-conversation message appears. **Sending** means the message is being submitted, not that the Agent has started. Activity comes from Node; when no specific action is available, the display says **Running** without inventing a reasoning summary. Run duration uses its start and completion times, including waits and continuation within that Run. Missing reliable timestamps hide the duration; a new Run after a Node restart starts a new clock.

Use the session list to reopen, rename, pin, reorder, or delete sessions. On supported Nodes, title search can find sessions in the current Workspace even if they have not been loaded into the list. Clear the search to restore the normal list. Search and pagination stay within the selected Workspace. Deleting a session also permanently deletes all of its child sessions at every level. This cannot be undone, but it does not delete Workspace files.

Working sessions hide Delete. If a session starts working during deletion confirmation, the operation is not submitted. Rename and Pin remain available.

On supported Nodes, choose **Session Prompt** from an existing session's More menu to save multiline instructions of up to 20,000 characters. Leave it blank and save to clear it. The setting belongs only to that session and survives reopening or a Node restart. It is appended after the sender's shared and Agent-specific personal instructions, without replacing account settings or appearing as an ordinary message.

Changes do not interrupt the current execution. They apply from the next execution, including queued messages, Goal continuation, and messages sent to that session through marctl. You can also [read, set, or clear the prompt with marctl](../operations/marctl.md#persistent-instructions-and-approvals). Clearing stops future injection; it does not remove old instructions already in the Agent's conversation history. Start a new session if you need to isolate old instructions completely. Hosted conversations do not offer this setting.

Sessions discovered from an external Agent appear normally. Their first message automatically validates and activates a safe continuation path; if validation fails, no Run is created.

After a Node restarts, sessions may appear in batches. A slower Agent does not delay sessions already found. Sessions keep their custom titles when they reappear in the list.

## Clean up sessions

Choose **Clean up sessions** from the current Workspace session list's More menu, enter 1–365 days (30 by default), and confirm. Sessions whose activity predates the selected cutoff and sessions whose activity time is shown as `—` are included. When evaluated individually, pinned, running, queued, recovering after a restart, or currently viewed sessions are kept. If the scan finishes and the Agent is available but a session is not found, cleanup may remove its list entry regardless of its age. This removes only the list entry, not the contents of the session that was not found.

Child sessions are evaluated by their own activity times. Deleting a parent also deletes all of its child sessions at every level, even if a child is recent, pinned, queued, or currently viewed. If any child is running or recovering after a restart, the parent is kept. Deleted child sessions are included in the totals.

Cleanup permanently deletes matching sessions and cannot be undone. It does not delete Workspace files. The dialog shows the actual deleted, skipped, and failed counts, including deletions by Agent.

If cleanup stops early with sessions left to process, the dialog shows **Cleanup partially complete**. Unprocessed sessions do not count as failures. **Not processed** shows the remaining count when known. Cleanup does not continue in the background; you can run it again. An offline Node or unavailable result still produces an error.

## Share a work session

Choose **Share conversation** from a regular work session's More menu. Expiration is optional; leaving it blank creates a permanent link. Creation shows share text containing the link and a random six-digit password. Choose **Copy** to copy the entire text. Existing records appear below; you can copy the same complete share text at any time, open their links, or delete them. For older records without a recoverable password, enter the original password once when copying. After verification, future copies work directly; the original link and password remain unchanged.

The header shows the session title and Workspace name. Visitors enter the password to open a standalone chat without a Console account. Access credentials, the anonymous visitor identity, and the name requested before the first message are saved in that browser and restored after refresh or reopening. The Participants panel lists the sharer first, followed by participants viewing any share link for the same session. Anonymous identity and name are shared across links in the same browser. Use the edit button beside your own visitor name to change it across open share pages. Canceling leaves the name unchanged and does not send a message. Visitor names match message authors and are never merged or hidden by Console sign-in; unnamed visitors appear anonymously. The fixed sharer entry shows the account nickname, falling back to the username. The sharer’s green dot appears only while they have a share page open and disappears when their last page closes. Display names do not grant authorization.

Visitors see the original session's entire history and future messages. They use its Agent and settings as the sharer, including messages, attachments, file and skill references, queuing, insertion, and interruption. Concurrent control uses the same shared state and mutual exclusion as opening the session in multiple browsers. The share page hides the model, reasoning effort, access mode, and context usage and its tooltip. There is no input prediction or Workspace management area. File links still open read-only previews, including separate file windows and Markdown or HTML rendering. Read-only mode does not prevent HTML scripts from running. Only preview trusted files; see [HTML preview risks](files.md#steps).

**Give the link and password only to people you trust.** Signing out as the sharer does not revoke a link; delete its record to stop access. Deletion or expiration immediately disables that link's chat pages and rejects further reads and messages, without stopping already accepted tasks or retracting content visitors have read. Other links and the original Console remain available.

## Automatic continuation after orderly shutdown

In regular Workspaces, MAR Agent can continue after Node receives `SIGTERM` or `SIGINT`, finishes an orderly shutdown, and starts again. A later manual start after a normal stop also qualifies. After reconnecting to Server, Node rechecks current user and model authorization before restoring unfinished work, Goals, and the message queue in the same session. A previously paused queue stays paused. New messages and queue changes are temporarily blocked for that session during recovery.

Ordinary runs show a “System restart continuation” history entry, not a message attributed to manual user input. An active Goal gets one Goal continuation without an additional ordinary continuation. The prompt asks the Agent to inspect the current state after a system restart before continuing. Old tool processes, terminals, approvals, questions, and background cells are not restored, and external actions are not guaranteed to happen exactly once. Queued inputs are prepared again in their original order, including their attachments; old attachment preview URLs are not guaranteed to remain valid.

Unexpected exits, forced kills, power loss, failed handoffs, other Agents, hosted conversations, and administrator-controlled upgrades are excluded. Lost access, unavailable models, or inputs that cannot be rebuilt never bypass validation; check Node diagnostics and take over manually. A handoff is consumed once, not retried on every startup.

## Navigation

The session list, Recent Sessions, and Quick Open open sessions in Main. Clicking a notification in the panel, a browser system notification, or an [unread Workspace tab](navigation.md) keeps an already selected Main session in place. If the session is open only in Aside and Aside can be shown, the jump activates it there without replacing your Main session. On desktop, a brief outline shows where it opened. If the session is not open or Aside cannot be shown, it opens in Main without closing any existing Aside tab. Explicit **Open in Main** and **Open in Aside** actions still use the pane you choose.

Clicking the selected Workspace tree entry or jumping to an already open session does not explicitly refresh content or reset your reading position. Repeated selections also leave an in-progress load alone. Use the corresponding refresh action when you need updated data.

## Scheduled tasks

Open the calendar-with-check icon beside **Work** to see **Scheduled tasks**, or open it from an existing session's menu to filter the same page to that session. **My schedules** shows tasks you currently own and can still access. **All schedules** includes other tasks you can see. Both pages can be filtered by Workspace; the node name distinguishes Workspaces with the same name. Task cards load 20 at a time. Select a page on desktop, or scroll to the bottom on mobile to load more automatically. Each task card shows its next run. Offline nodes may show only their last synced task summaries; editing and viewing execution records require an online node.

**Session schedules** shows the current session name even if it has no tasks. Select **Back to all schedules** to return to the global list. New schedules created here are locked to this node, Workspace, and session. Opening a conversation notification leaves the schedules page and shows the target conversation.

1. Select **New schedule**, then choose an online node, a Workspace, and a run target. Reuse an existing session or choose **Create a session each time** and select an Agent and a fixed model. Selecting a model sets its default reasoning effort, which you can change if the model supports it. Existing sessions use their settings at trigger time. Hosted conversations do not support scheduling.
2. Enter a name and a task prompt. In **Run times**, add one row for each clock time. Set it to **Once**, **Daily**, **Weekly**, or **Monthly**. For **Once**, the node suggests the next date for that time; you can change it. Weekly and monthly schedules can select multiple weekdays or days of the month. If a month has no day 31, that date is skipped. Overlapping times within one task trigger only once. Create separate tasks if different times need different prompts.
3. Check the upcoming triggers in the displayed Node time zone and save. The task runs as its current owner. Saving an edit or accepting a proposal on the web makes you the owner. Opening, cancelling, or rejecting a proposal does not. Run notifications are off by default. Enable them if you want alerts; turning them off keeps the execution records and does not suppress change-proposal notifications.

Only one-time schedules can catch up after a missed time, within the wait limit you set. Catch-up is off by default. After upgrading from the old scheduling format, existing tasks are paused until you set new run times. The tasks and execution records are kept.

On supported nodes, **Run times** also offers **Hourly**. Select minutes instead of a clock time. The default is `00` (on the hour); selecting `15` and `45` runs the task at :15 and :45 past each hour. You can combine it with other rules; matching rules trigger only once in the same minute.

If you have access to operate the Workspace, click an online task card to edit it, even if someone else created it. Workspace members with access can also delete tasks and resolve proposals. Offline tasks cannot be edited or deleted. If a saved fixed model is no longer selectable, you can keep that target and edit other settings. The model must still be available at execution time. Use the linked session control on an online card to open that session. **Execution records** on a card opens that task’s records without leaving the list. The **Execution records** section in the navigation shows all authorized tasks and can be filtered by Workspace. On desktop, switch pages below the table. On mobile, scroll to the end of the table to load more records. Open a record to see the prompt at trigger time and any recorded start and end times. When you have access to the original run, the details also show its ID and status and let you open the session where it ran. Renaming a task or changing only its prompt does not reschedule it; changing the run times or re-enabling a task recalculates upcoming triggers. **Schedule finished** means there are no more dates, not that every run succeeded.

A session with an enabled task that still has upcoming triggers is pinned and shows the schedule icon. Pausing, finishing, or deleting a task does not automatically unpin the session. Pausing keeps the execution records; deleting the task removes them. If a trigger is still being processed, pause the task and wait for that trigger to settle before deleting. Deleting the target session pauses its tasks and marks them for rebinding rather than switching them to create new sessions.

If a task did not run, inspect its execution record. A busy session or an unavailable service can cause a recurring trigger to be skipped without a bulk catch-up. A trigger matching a specific date can wait within the configured limit (0–60 minutes; new tasks default to 0, meaning no waiting). The owner must still have permission at execution time; waiting does not bypass that check. **Outcome unknown** does not prove the task did not run, so verify the run or external result before repeating it manually.

Scheduled runs automatically approve tool permission requests, including third-party MCP tools; Agent sandboxes and host restrictions still apply, and questions still need user input. In a regular Workspace, MAR Agent uses the built-in `marctl` skill when available. Without it, or with another supported Agent, the built-in `mar_schedule` MCP can list, read, create, and update the current session's tasks and read their trigger records. No installation is needed. An update requires the task and its current revision; edits to another user's task become proposals that authorized Workspace members can resolve on the web. For cross-session task management in the authorized Workspace, see [Scheduled tasks with marctl](../operations/marctl.md#scheduled-tasks). These tools do not manage system schedulers or CI.
