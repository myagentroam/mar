# Conversations, Tools, and Notifications

**Recent Sessions** also provides **Main Sessions / Child Sessions**, defaulting to Main Sessions and following the [session list rules](sessions.md). Tabs have no running or unread badges and only switch the list, without opening a session; the total running count appears within Recent Sessions. Opening a notification, recent-session item, or Workspace tab synchronizes the target session's group in Chats; individual session indicators stay unchanged.

Conversation groups your messages, Agent replies, reasoning summaries, plans, commands, tools, file changes, approvals, and questions in execution order. Expand supporting cards when details are needed; Agent Markdown is sanitized before display.

Expand a file-read entry to see the actual line range and corresponding content when supplied by the source. Older records and Runners without per-file associations retain the overall call result. Skills, commands, web calls, and other tools show details supported by their available facts; image-view tools show metadata when no preview is available. Results can be truncated by the source or display limits. The copy button copies the call's public record without rereading a file or webpage.

Cross-session message headings distinguish parent, child, descendant, and other sessions using the saved sender name. Hover to see the source session ID. Older messages without a saved relationship retain their original source label.

Images in the conversation load as thumbnails. Click one to open an aspect-ratio-preserving preview, shown only after loading and decoding finish. Detail previews fit within 2560×2560 without enlarging small images. If a preview was resized, **View original** appears at the top right. This loads the original image while still fitting it entirely within the dialog, preserving its aspect ratio without cropping or image scrollbars. Long screenshots also fit as a whole, so their text may appear small. Failed loads can be retried. This does not change uploaded files or images sent to the model.

Within the same conversation segment and aggregation phase, reasoning, ordinary tools, commands, and file changes each share a card positioned at that type's last item. Adding another item of the same type moves the whole group to that item's position, while members retain their original order. Streaming content or status updates to existing items do not move cards. Groups never span segments or user turns, and new activity after an Agent reply does not merge into cards before that reply. Image generation, plans, approvals, and questions remain separate.

Context compaction appears separately and marks a work-process boundary, including background compaction. Subsequent reasoning and tools start a new process instead of merging with earlier records. Compaction status updates do not repeatedly split the process or mean that the current task has ended.

All four Runners use **Agent operations** groups, not limited to parent-child sessions. MAR Agent supports start, send, wait, stop, list, and view; other Runners show their native operations. Agent operations within the same work process and aggregation interval share one group positioned at the last call, regardless of target, operation, or target count. The group header shows the call count. Expand it to see each call's original tool name, available task names, and own status in the original order.

Details present facts supplied by the source: start and send focus on the task name and current message. Queue/steer describes the sending mode, not confirmed delivery or processing. Wait and view show the status, message, or result returned by that call; list shows session names and statuses; stop displays the public result as-is. Use the copy button at the top right for the original input, result, and other available public fields. The record is bounded and does not fetch additional target-session data. Older records without structured facts retain generic details, where model metadata appears only when supplied by the source. A returned call does not mean the target task has finished, and a wait timeout does not mean it failed; error information is retained. The target session's internal execution stream is not embedded, and cards do not provide session shortcuts. Use the session list or session tree to open a target session.

When an Agent request or model call finally fails, the error card shows the HTTP status when available and the returned error message. In an ordinary session, a terminal failure returns the session to Idle and pauses any remaining queued messages until you resume the queue or send a new ordinary message after reviewing the error. MAR Agent may retry eligible transient model failures before its first semantic output; an active Goal may also retry failed executions through bounded automatic continuation before blocking.

## Inspect this file change

Supporting MAR Agent Nodes save a read-only Diff for each `apply_patch` operation, in both Direct and Code Mode. Expand a file-change card to see trusted green `+N` and red `-N` counts at the end of each entry. Click a file to open **This change**, with single-column added and removed lines for additions, deletions, edits, and both paths of a move. Overwriting an existing file is shown as a modification. Added or deleted empty files still show their path change with `+0/-0`, without inventing an added line.

This is that operation's historical change, not the task's cumulative change or the current [Git changes](git-changes.md). Separate edits to the same path open independently. Later edits or deletion of the current file do not alter a saved Diff. The shared **Open source file** button and `Ctrl+E` (`Command+E` on macOS) open the current source file through the normal file-opening flow, not the raw Diff text. The saved change remains read-only and separate from the current source file. If that file is missing or inaccessible, opening it reports an error without replacing the saved Diff. Failed reads can be retried and never silently fall back to the current Git Diff.

Other Runners, older history, and Nodes without resource-reading support retain their previous file-opening behavior. Unknown counts are not replaced with zero. Non-text files, size limits, and storage failures show an explicit unavailable-details notice. Arbitrary writes by shells, scripts, or formatters are not captured. Clearing, truncating, or deleting session history removes its unreferenced Diffs; Rewind branches retain Diffs referenced by their copied history.

## Create a non-destructive branch from a message

For MAR Agent, Codex, Claude Code, and OpenCode, completed user and Agent messages show Rewind beside Copy when the history contains a usable boundary. After confirmation, Rewind creates a new session branch. Rewinding a user message branches before that turn and restores the original text to Composer; rewinding an Agent reply retains the complete turn and leaves Composer empty.

Rewind does not modify the original session or roll back Workspace files. While Working, submitting a message, or changing a session, the UI hides Rewind and Rollback, locks model, reasoning effort, access and manual context compaction controls, and hides commands that require an idle session. Copy, queueing, stopping and state commands that support execution while working remain available. If the session starts working or the selection changes during confirmation, the operation is not submitted. Rewind is not restricted by Session capability or App Server probing. If the Agent, its version, or a session lock held by another client still rejects the branch, the current session and draft remain unchanged and the actual error returned by Node is shown.

Completed user messages also show Rollback after Rewind when the session declares native history-truncation support. MAR Agent supports it; Codex supports it only for native `paginated` sessions, not legacy history. Claude Code and the currently integrated OpenCode history API do not provide a compatible history-only truncation operation. After confirmation, Rollback does not create a branch: it permanently removes the selected user message and all later history from the current session, then restores the original message to Composer. It never rolls back Workspace files. The session must be idle with no queued messages. A failed request shows the actual error without optimistically changing the displayed history or draft.

Rolling back a steer message added during a MAR Agent run preserves ordinary messages and execution records from before that input was received, whether or not it had taken effect before stopping.

## Live performance

When the Agent provides valid timing metrics, a small Info icon appears at the bottom right of the Workspace conversation. Hover, focus, or tap it on a touchscreen to see the latest Latency (from the current input to its first text, reasoning, tool call, or other valid model response) and available average output TPS (tokens per second). Each value describes its latest available observation, not an individual message or the whole tool chain. Tool execution time is excluded from Latency, and missing metrics are not estimated. MAR Agent shows average output TPS only after the request ends, the provider reports authoritative output tokens, and a reliable streaming generation window is observed. It is the client-observed average from the first actual generation delta to completion; completed-only, single-delta, or instantaneous batched output does not produce a new TPS value. Available TPS may include reasoning, tool-call, network, or Hosted Tool time, so it is not pure server-side inference speed. For Claude Code, Codex, and OpenCode, Node observes Latency from live events: submitting user input to the first valid Agent response, then the last observed parallel tool result to the next valid response. This includes Runner, IPC, and network overhead, not pure model-server response time. These three Runners currently do not provide output TPS.

Performance is pushed live and is not stored in session history. The active process heading also shows available metrics for the same Run after its duration; the Info icon remains available. Within the same Run, Latency and output TPS update independently: new Latency keeps the most recent available TPS until new TPS arrives. The two values may describe different model requests. A new Run does not inherit the previous Run’s metrics. Node keeps only the latest metrics in memory while the Run remains active. Returning to a running session or refreshing the page restores them automatically; a Node restart loses them. Node clears the metrics when the Run ends. The current page may keep the final values, but returning after completion does not restore them. Switching sessions, Workspaces, Nodes, or modes first clears the previous metrics from the page. Message cards do not show performance Info.

## Clear a MAR Agent session history

In the Composer for the current MAR Agent session, enter `/clear` and select the command. After confirmation, it permanently clears all history and session images while retaining the same session, title, Workspace, and current configuration. It does not delete the session or roll back Workspace files. The operation is rejected while the session is running, has queued messages, or is already changing history; the existing history and draft remain unchanged.

## Clean up Workspace sessions

On Nodes that support it, choose **Clean up sessions** from the workspace-level more menu at the upper right of the current Workspace's **Sessions** pane. Enter how many days of inactive sessions to clean up; the default is 30 days. Matching native sessions are permanently deleted through the deletion capability supported by each Agent. Sessions with unknown activity times are included; pinned, active, queued, or viewed sessions are kept. When it completes, the page shows deleted, skipped, and failed counts, plus the actual deletion count for each Agent, and refreshes the current Workspace session list. After complete discovery, local-only records belonging to an available Agent are removed directly without extra native-presence probes, regardless of age; pinned, active, queued, or viewed records remain protected. Reaching the time budget returns settled partial counts, not failures for unprocessed records. You can run cleanup again; see [Clean up sessions](sessions.md#clean-up-sessions).

Approval cards require an explicit allow or reject action. Question cards require every answer before submission. File-change cards open the related diff when possible.

The notification center reports completed or failed runs, approvals, questions, plans, and uploads. When the target regular session or hosted conversation is active in the current browser, its notification is marked as read without opening a preview; other signed-in browsers synchronize the resulting state. Explicitly interrupting a regular session, or stopping or deleting a hosted conversation, does not create a terminal notification. Run, approval, question, and plan notifications remain on Server for 24 hours and are reloaded after a refresh or live reconnection without replaying their popup. Hosted conversations create notifications only when a Run succeeds, fails, or ends because of an unexpected interruption; they do not create approval, question, or plan notifications. File upload and stop notices remain local to the current browser. File upload notifications are read immediately and do not increase the unread count, but still show a brief preview. Selecting a regular notification opens its Node, Workspace, and session when they remain accessible; selecting a hosted notification switches to Conversation mode and opens its conversation.

**Sessions & notifications** is one main-navigation entry after **Chat**, with no separate top-right bell. Its upper-right number counts unread notifications (`99+` above 99); its lower-right green dot indicates active regular sessions, including those starting or cancelling. Opening the panel selects **Notifications** when unread items exist, otherwise **Recent Sessions**. New notifications and marking all read do not change the selected tab while the panel stays open. Opening alone does not mark items read. Notifications retains uploads and regular or hosted-conversation notifications. Recent Sessions retains active regular Workspace sessions and up to 100 finished tasks from the last 12 hours; hosted conversations are excluded. Active tasks appear first, ordered by start time from newest to oldest. Finished tasks follow in completion-time order, falling back to their last update time. Selecting an item opens its Node, Workspace, and session. Desktop panels and previews open beside the left entry; mobile uses the auxiliary menu below the top bar. Tabs and actions stay fixed while lists scroll. Previews do not replace an open menu or steal focus. Deleting a notification does not remove a recent session. A user stop explicitly identified by the Node is labeled **Canceled**; other interruptions and older records without a stop reason remain **Interrupted**.

After reconnecting, returning from the background, or regaining window focus, a visible and focused page checks and marks unread notifications for the same active regular session or hosted conversation. You do not need to switch sessions. Returning to a selected work session or hosted conversation through the top navigation also marks that target as read. Other conversations keep their unread state. Clicking a notification in the center or a system notification marks only that item as read, not other notifications for the same target. Badges update only after Server confirmation; a failed read request does not clear the count locally and is retried on the next connection or focus recovery.

Use `Ctrl+Shift+E` (`Command+Shift+E` on macOS) to quickly open or close the combined panel.
