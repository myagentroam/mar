# Work Mode, Nodes, and Workspaces

Console provides two parallel modes: **Work** and **Conversation**. Work is the new name for the former **Nodes** top-level entry and opens the same Node → Workspace resource tree. Node management, Workspace tabs, Agent sessions, files, Git, and terminals work exactly as before. Conversation mode starts and continues conversations from published templates.

In Work mode, expand a Node group in the left resource tree and open a registered Workspace. Node rows organize resources and expose host management; clicking a Node name only expands or collapses its group and never changes the active Workspace. There is no separately saved current Node.

Every Workspace uses the same activation path: its tab activates and restores cached content immediately, then refreshes in the background. An uncached target shows its own loading state without waiting for network responses before selection. A temporary network failure leaves the target selected so it can be retried. Confirmed missing or inaccessible Workspaces have their content cleared and follow tab removal and fallback rules. Newer selections take precedence over late responses.

Clicking a Workspace tab, including the active tab, desktop overflow menu, or mobile strip, first opens its first valid unread session. A successful open marks only that session read; unread indicators remain for other sessions, and another click opens the next unread session. With no unread sessions, the first active task takes priority; otherwise the tab restores its last selected session, or keeps the existing empty or draft behavior when none is available. Candidates follow their existing order, regardless of session-list pagination or search. A failed open does not clear unread state. Background notifications and task changes never switch sessions automatically, and navigation never starts or stops tasks. Tree navigation, shortcuts, and fallback after closing a tab keep their existing behavior.

Workspace registration uses an explicit host target in a dialog; closing it leaves the active Workspace unchanged. Open Workspaces appear as tabs and retain their order in the current browser.

On desktop, drag the divider at the right edge of the Workspace tree or the left edge of the files panel to resize it within its minimum, maximum, and available space. Widths are saved in the current browser's localStorage and restored after a refresh. First-time use or invalid saved values use the default widths. Horizontal resizing is unavailable when the files panel stacks below the conversation on a narrow screen or panels use mobile drawers; these layouts do not overwrite your desktop preferences.

Right-click a Workspace tab and choose **Pin** to move it to the end of the pinned section. Pinned tabs replace the close button with an always-visible pin icon; click it or choose **Unpin** to return the tab to the start of the normal section. Pinned tabs can be reordered among themselves. Dragging a pinned tab after a normal tab automatically unpins it; dragging a normal tab into the pinned section pins it automatically, while dropping it at the section boundary keeps it normal. Pin state and order survive a refresh. When desktop space permits, pinned tabs stay visible while normal tabs scroll. If too many pins leave insufficient space for a normal tab, or on mobile, the full strip scrolls; use the all-open-Workspaces menu on desktop or swipe horizontally on mobile to reach overflow tabs.

**Move left** and **Move right** move a tab one position, with invalid moves disabled at the ends; crossing the section boundary also pins or unpins the tab automatically. Opening the menu, pinning, or reordering does not switch the active Workspace or change LRU activity times. Up to eight normal tabs are retained; opening more evicts the least recently used normal tab. Pinned tabs do not count toward this quota and are never evicted. If unpinning exceeds the quota, the newly unpinned tab remains and another least recently used normal tab is evicted.

Use `Ctrl+W` or `Alt+W` to close the active normal tab and `Ctrl+Shift+W` or `Alt+Shift+W` to close all normal tabs; on macOS, use `Option` instead of `Alt`. Pinned tabs remain open and their **Close** menu action is disabled. These close shortcuts also work in Composer; other inputs, editors, terminals, and dialogs retain their native behavior. Double `Esc` no longer closes Workspace tabs. Ctrl combinations work when the browser or PWA delivers the key event to the page; use Alt combinations if the browser intercepts them. Closing the active tab returns to the most recently used remaining tab, regardless of pin state or display order. If a target is permanently unavailable, the next recent tab is tried; if no valid tabs remain, no Workspace is selected. Temporary network failures do not switch back to the old tab. A newer user selection takes precedence over pending fallback results. Closing an inactive tab does not switch Workspaces. Closing a tab clears its cache and closes its terminals, but does not unregister the Workspace or stop running Agents. See [Keyboard Shortcuts](../reference/keyboard-shortcuts.md).

An offline or disabled Node keeps its registered resources visible but blocks live operations. Existing tabs still activate immediately; reconnect or enable the host before using files, sessions, or terminals. Closing a Workspace tab changes only the browser layout; it does not unregister the Workspace or stop Node work.

On mobile, use **Work** in the top bar to open the same resource tree. Selecting a Workspace closes the drawer and returns to the Agent conversation. Use **Chat** to enter Conversation mode; selecting it again while active opens the chat-history drawer. The top-level navigation contains Work, Chat, Admin, and Settings. Admin no longer has a separate Skill Center entry. Skill Configuration, Skill Sources, and Environment Secrets appear consecutively, while MCP Sources remains a separate Admin section; Skill Configuration switches between Skill and MCP in the page.

Settings contains Account Security, Appearance, System Notifications, Quick Prompts, Personal Instructions, Keyboard Shortcuts, and About. Personal Instructions provides additional guidance for later Agent runs by the current account and saves Common, MAR Agent, Codex, Claude Code, and OpenCode values separately; the MAR Agent label remains `MAR Agent` in every interface language; each run combines Common with the current Agent's instructions without modifying Node or Workspace `AGENTS.md` or `CLAUDE.md`. Appearance defaults to the dark color theme and Material file icons, with light/dark color themes and Seti/Material icon themes available. Changes apply immediately and are saved only in the current browser; valid saved choices are not overridden by the defaults. About shows the current Web version, links to the documentation center, and groups major open-source components across Web, Server, Node/MAR Agent, bundled tools, icons, and the optional Computer Use Runtime. This is a selection, not a complete dependency inventory. "View Web third-party notices" covers Web only; consult the corresponding Server, Node, and optional runtime distributions for their license and notice files. Node bundles tool materials under `vendor/ripgrep/` and `vendor/ctags/`. External Agents, SDKs, and separately installed tools remain subject to their own terms. Runtime status and License management remain under Admin > System Information.

## Themes

Themes stay only in this browser. They are not uploaded or synced with accounts or devices. Clearing browser data deletes custom themes; export JSON files for backup or manual transfer.

1. Open **Settings → Themes**. The theme picker shows color swatches for built-in light, default dark, and saved themes. Select a theme to inspect it without changing the active palette; use **Apply theme** to switch. Built-ins can be viewed, copied, and exported, but not overwritten or deleted.
2. Open a theme’s more-actions menu and choose **Duplicate** to start with its complete palette, or **Import JSON**. Import does not overwrite themes with the same name. Copies and imported drafts both need saving.
3. Edit JSON on the left. The compact preview uses static examples of lists, messages, code/diffs, status indicators, inputs, and buttons, not actual project content. Hover or use Tab to inspect control states. **Enlarge preview** opens the same sample at normal text size. On narrow screens, the preview appears below the editor. Editing does not change the active global theme.
4. **Save theme**, then use **Apply theme** in the picker or select it under **Settings → Appearance → Theme**. Applying a saved theme does not replace the open draft. Saving changes to the active theme updates its colors immediately. Save drafts before leaving the page.
5. Copy JSON, format, or export it. **Reset** requires confirmation and restores the last saved JSON or the original imported/copied draft without deleting the theme. Delete from the theme’s more-actions menu, with confirmation; deleting the active custom theme restores the default dark theme.

JSON uses `version: 1`, `name`, and `colors`, not `base`. The colors object maps tokens to values, for example `--mar-bg-panel` to `#ffffff`. Colors accept `#RGB`, `#RGBA`, `#RRGGBB`, and `#RRGGBBAA`. Missing or invalid colors always use the corresponding default dark colors; saving does not expand the original JSON. Expand **Supported color tokens** for all keys. Duplicating a theme materializes its complete effective palette without depending on the source theme.

Only **invalid JSON syntax** blocks saving or exporting. Missing names, unknown fields or tokens, invalid colors, and low contrast produce advisory warnings. Saved and exported JSON retains unknown and invalid content, but it is ignored when applied. An old `base` field is also retained with an unknown-field warning; it no longer changes the dark fallback rule. Arbitrary CSS, URLs, and scripts are not executed. Contrast checks cover only explicit opaque color pairs, not a complete accessibility audit.

Themes do not change layout, fonts, file icon themes, the fixed terminal palette, the marketing homepage, or public help. The preview is a representative color sample: it does not perform real workbench actions or cover unaffected areas such as terminals.

## System notifications

Choose **Settings → System notifications → Enable system notifications** and allow the browser permission prompt. The opt-in is off by default and saved for this account in this browser. Signing out does not revoke the browser permission.

When Console loses focus or becomes hidden, new Agent run, approval, plan, user-input, and scheduled-task notifications can appear as system notifications. Switching to a terminal or IDE can trigger reminders even if Console remains visible. A focused Console does not show system notifications and keeps the existing read behavior for the active target. Clicking a system notification focuses or opens Console, marks only that notification read, and locates its session or conversation. Deleted, expired, or another account's notifications do not open a target.

Windows, macOS, and Linux use the same browser notification interface. Banners, sounds, and placement depend on the browser and operating system. Use HTTPS or a trusted localhost origin with a browser supporting the Notifications API and Service Workers. If permission is denied, allow this site manually in browser settings. The app cannot automatically open internal browser or system settings across platforms. System notification failures do not affect the in-page center.

An administrator can enable the default-off **Web Push** switch under **Admin → System Configuration**. The deployment needs a valid public HTTPS origin, and the switch cannot be enabled while delivery is unavailable. The same personal system-notification setting then registers this browser for offline Push; choose **Enable offline Push** if action is required. One account can register independent clients on multiple devices or browsers; disabling one does not disable the others. Reloading checks the system switch and subscription again.

The page separates **Online system notifications** from **Offline Push**. Enabling online notifications does not mean offline Push is ready. **Disabled by the administrator** means an administrator must enable the system switch. **Server is not configured** means delivery capability or the public HTTPS configuration is not ready, not that this browser denied notification permission. The production Server includes the sender; an administrator should check the deployment's public origin before enabling the switch.

MAR uses the browser's HTTPS subscription endpoint through standard Web Push without restricting push providers, endpoint domains, addresses, or ports, and without IP pinning. This does not guarantee background delivery in every browser: the browser still needs a working push channel and system notification permission. Deployment network policies are responsible for isolating Server outbound access.

If any authenticated, handshaken workbench WebSocket for the same account remains open, the Server suppresses Web Push to every registered client for that account. Node and Terminal connections do not count as online. On desktop, the existing system-notification path can still alert while an online page is unfocused. Mobile clients do not show online system notifications; the existing settings and offline Push remain unchanged. A mobile client in the background still receives no Push while a workbench connection remains open. Both paths share notification identifiers and the same center. Explicit email is unaffected by online status or Push settings. Notifications skipped while online or disabled are not replayed. After all pages close, the Service Worker can receive best-effort Push, without a delivery guarantee.

Capability detection covers Chrome, Edge, and supported iOS/iPadOS 16.4+ Home Screen web apps; ordinary iOS tabs are not guaranteed. On iOS, add the app to the Home Screen, launch it there, then explicitly allow notifications. Initial permission requires a click; individual clients do not require developer-app registration. A fully closed browser, offline network, sleep, power saving, Do Not Disturb, or OS policies may prevent display. Logout invalidates the sending Session and local display binding. Late messages with an unconfirmed binding show only a generic prompt whose click opens Console.

If no banner appears, check the site's browser permission, the browser or installed app's system notification setting, and Do Not Disturb. Plain HTTP intranet addresses usually do not support this feature; use HTTPS.

## Personal usage

Open **Settings → Personal usage** to review Conversation usage for main agents and subagents by default. **Conversation**, **Compact**, and **Composer Prediction** are separate categories; title generation and other requests are also available. Compact and prediction are excluded from Conversation. Switching categories updates the rolling last 24 hours and last 7 days (168 hours), charts, and records together. Top summaries for the current category do not change with the filters below. Filter charts and records by time, Runner, model, and Work/Conversation mode. Times use the browser time zone shown on the page.

The visible page refreshes every 60 seconds and pauses when hidden or closed. Failed refreshes keep the existing data and retry later. While paging, sorting, or expanding records, summaries keep updating but records remain in place; choose **Update records** or **Refresh** to return to the latest first page. Records load in batches of 20. On desktop, the standard management pager shows the actual filtered record count and page count and supports direct page jumps. On mobile, scrolling to the bottom loads more; you can also select **Load more** to append the next batch. Column sorting applies to the current desktop page or the already loaded mobile records. Changing filters or explicitly refreshing resets the loaded records. Custom date ranges stay fixed during automatic refreshes. The last refresh time does not mean every Node has finished syncing.

Input includes cache reads and writes; output includes identifiable reasoning tokens. Cache and reasoning details are not added to the total again. Main and subagent conversation requests, compaction, prediction, and title generation are recorded in their respective categories rather than mixed into Conversation. Failed or cancelled requests retain usage already reported by the provider. Missing token fields are recorded and displayed as 0. Total tokens are input plus output; later usage updates revise the same record.

Summaries, filtered totals, trends, Runner/model distributions, and records show cache-read tokens with the hit rate in parentheses (recorded cache-read tokens divided by recorded input tokens). Aggregate rates are token-weighted, not averages of per-request percentages. The cache-colored segment is part of input and does not increase the bar height or total. Tooltips and expanded records list cache-write tokens separately. Unreported cache counts display 0. Missing or zero input produces a 0% hit rate. Time buckets without requests also display zero. This recorded-usage convention does not mean the provider confirmed zero consumption.

Nodes queue usage and resend it after reconnecting, so historical charts may change. Previously received records remain available while a Node is offline. Server records are retained for 90 days; pending Node records are bounded by capacity and retained for up to 7 days. Collection starts when the feature is enabled; old sessions and external CLI history are not imported. External Runners may not expose every request. These statistics are not a provider bill or remaining quota. Usage belongs to the person who initiated the input, not the credential or Node owner. You can view only your own records.
