# Manage Nodes and Workspaces

Node and Workspace management lists request 20 entries per page, after the Server applies management scope, filters and ordering. Work-mode resource trees and resource selectors still read their complete authorized scope, independently of the management list page.

Install Nodes separately and register them with the Server. Standard personal or organization resource permissions apply; the Server never creates or runs a Node automatically.

In the **Work** resource tree, both Node and Workspace **More** menus offer **Move up / Move down**. Workspaces move only within their current group, including the ungrouped list. On desktop, you can also drag Node names or Workspaces within the same group to reorder them. A top or bottom line on the target row indicates insertion above or below it. The corresponding action is disabled at either end, and ordering is disabled while filtering. Local ordering needs no resource management permission and does not change the active Workspace, top tabs, or group membership. The order is saved only in the current browser tab and restored on refresh; it does not sync to an account, organization, or another device.

In **Admin → Nodes**, create a registration key. On success, the form closes and a separate confirmation dialog shows the key, instructions, and deployment guide. Copy and save the registration key before closing, then follow the deployment guide to register your device. Each key can only be used once. The Node appears in the list once it connects. Review its platform, Node/Server versions, connectivity, supported Agents, environment, and upgrade state. Push upgrades only to Supervisor-managed Nodes after reviewing the run-drain and terminal impact. **Push all** confirms the impact, then requests an upgrade for every eligible, online Node in the current management scope, regardless of filters or pagination. Ineligible Nodes are skipped; partial failures list the affected Nodes and reasons. The target is the highest published stable npm version that meets the business baseline and does not exceed the current Server version, sent as an exact version.

Workspace groups are managed in the **Work** resource tree, not in **Admin → Workspaces**. A user with the same Node permission required to register a Workspace uses **Move to Group** in a Workspace's **More** menu: choose an existing group already loaded for that Node or enter a new group name; save an empty value to remove the Workspace from its group. A Workspace can also be dragged onto a group heading to move it there, or onto an ungrouped Workspace or its own Node row to remove its group, even when no ungrouped Workspace exists. Dropping a Workspace onto another Node is not supported. Dragging within one group changes only the current browser's display order. In Work mode, the tree is **Node → Workspace group → Workspace**: named Workspace groups appear first in name order and can be expanded to reveal their Workspaces; ungrouped Workspaces follow directly under their Node. Its filter searches only the Node names, Workspace groups, Workspace names, and paths already loaded into the resource tree. A Node match does not also show unrelated Workspaces, and the filter neither expands access nor requests more resources.

System administrators can govern all registered Nodes, including other users' personal Nodes. Workspace management remains limited to the administrator's own personal Workspaces and the authorized organization scope; it does not include other users' personal Workspaces. Node governance does not grant Agent, file, or terminal access.

In Work mode's Node → Workspace resource tree, use a Node row's **More** menu to open details or register a Workspace. After successful registration, the new Workspace opens and becomes active automatically. Use a Workspace row's **More** menu to open details, move it to a group, rename, or unregister it. Registering and grouping use the Node permission required to register a Workspace. Unregistering requires management permission for that Workspace; a Node usage grant alone does not authorize removal. Other write actions retain their own permissions. Renaming the top-level menu does not change these capabilities. Details remain viewable. **Admin → Workspaces** remains the place to inspect ownership and sharing. Unregistering does not delete host files.

Workspace unregistration commits separately on Node and Server; it is not atomic across them. If Node removed the registration but Server could not complete it, for example because authorization was revoked, a user who currently has management permission can retry. For an already removed target, Server continues its registration and relationship cleanup only when Node explicitly reports that exact Workspace no longer exists. Timeout, offline, busy, or denied responses do not prove absence; inspect status and current permissions rather than bypassing authorization or deleting host files.

In the Community state, Admin can enable or disable hosted conversations on an owned, online Linux Node that supports the operation. In the Enterprise state, shared hosting requires an organization-owned Node; personal Nodes in that state do not show the enable action. A previously enabled personal Node retains only the disable path so administrators can safely turn the capability off. The Node persists its private configuration and initializes hosting immediately, without a manual file edit or restart. Disable preserves the hosted directory, SQLite index, and conversation history. Node rejects disablement while a hosted Run is active or starting and never cancels that conversation automatically. Before hosting is enabled, the hosted-conversation storage maintenance area is hidden. After enablement, it shows hosted-directory usage, filesystem usage, and available capacity. If health checks fail, the maintenance area and enabled selection remain visible with the Node-reported unavailable reason. Usage at 85% is shown as high; at 95%, only new hosted conversation creation is blocked. Existing conversations remain available for reading, running, uploads, exports, and deletion.

When you can manage a Node, Node details provide a Computer Use switch that is off by default. Enabling it first reports **Initializing** while the Node downloads an exact managed Python/PyAutoGUI Runtime version from npm, verifies it, installs it into Node-private storage, and probes the interactive desktop. Node never invokes pip and never falls back to system or Workspace Python. The initial release supports only Windows x64 and Linux x64; other platforms report that Computer Use is unsupported. An unpublished, failed, or damaged Runtime package makes Computer Use explicitly unavailable without blocking the Node or other Agents. Reopen Node details or use the existing refresh action to see whether GUI control is available and, when it is not, the reported reason. Windows requires the current interactive user desktop, and Linux supports only X11 environments with reliable input injection; Wayland is not reported as available. Probes check screenshots and platform permission/backend evidence without test clicks, typing, pasting, reading or replacing clipboard contents. A successful screenshot alone does not establish desktop control: missing input permission, an unavailable clipboard backend, or insufficient evidence keeps Computer Use unavailable. Linux requires XTEST and an available xclip or xsel clipboard backend. Disabling the switch releases Computer Use resources without stopping unrelated Agent runs.

Choose an inactivity threshold from 1 to 365 days and preview the aggregate candidate count and reclaimable bytes before confirming permanent cleanup. Node re-evaluates candidates during execution and skips conversations with an active run, settlement, watch, upload, or permanent-deletion move; a preview is not a deletion list. Automatic cleanup runs every 24 hours with a default 60-day threshold. A user-confirmed conversation deletion is immediately permanent and has no recovery window.

When you can manage the owning Node, both its Node details and Workspace details provide access to the same Node environment secrets. Workspace management permission alone does not reveal or grant control of Node secrets.

Before deleting a Node registration, stop active Agents and close terminals. Deletion removes Server credentials and grants; the host must use a new registration key to register again.

Node management only sends upgrade intent; the host's existing Supervisor performs installation. It never creates Linux systemd units, Windows scheduled tasks, or macOS LaunchAgents, and never elevates privileges. Complete platform-specific automatic startup through [Install and Register a Node](../deployment/node-installation.md) first.

### Long-running Computer Use tasks

An ordinary MAR Agent session with Computer Use enabled can execute bounded desktop scripts. Execution waits for completion by default. The Agent can instead set `yieldMs` to receive a task ID early, prepare the next coordinates or do other work that cannot affect the desktop, then use `mcp__mar_computer__wait` to retrieve the final result and screenshot. Only one task can operate the desktop at a time. There is no independent cursor: do not use the same desktop concurrently, and do not assume another monitor isolates mouse or keyboard input.

A wait timeout does not stop the task. The Agent can explicitly cancel it; stopping the session execution or disabling Computer Use also cancels the task and drains cleanup. `STOPPING` means cleanup has not finished. With `OUTCOME_UNKNOWN`, some actions may already have happened: never replay automatically, and observe again. Early return improves responsiveness but does not promise faster drawing or a shorter total duration.
